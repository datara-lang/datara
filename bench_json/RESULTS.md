# bench_json — stdlib.json vs C, 10 MB (PLAN_V152 N3)

Machine: Windows 11 (26200), 64-bit. Date: 2026-11-03.
Workload: `data_10mb.json` — 10.00 MB (10 485 803 bytes), 124 259 flat
records, generated by `gen_json.py` (deterministic, ASCII).

C side: gcc 16.2.0 -O2 AOT (`json_c.c`, hand-rolled RFC 8259 recursive
descent + extraction pass). Datara side: `forgen run` (Cranelift native)
+ C runtime; validation by `stdlib.json.reader` (new recursive-descent
validator), extraction by the stdlib string surface (index_of →
substring → to_int — the same primitives `stdlib.json.parser` uses).

**Identical semantic workload on both sides:**
1. VALIDATE — full grammar walk of the whole document (objects, arrays,
   strings with escapes, strict numbers, literals).
2. EXTRACT — scan the top-level array; per record extract `id` (Int) and
   `name` (Str) length; accumulate sum(id), sum(len(name)).

## Results (3 runs each, median)

| Phase        | C (gcc -O2) | Datara (Cranelift) | Gap    |
|--------------|-------------|--------------------|--------|
| VALIDATE 10 MB | 14.0 ms   | 171 ms             | 12.2×  |
| EXTRACT (124 259 records) | 23.5 ms | 111 ms    | 4.7×   |

**Correctness: bit-exact.** Both sides report the same ground truth:

```
RECORDS 124259
SUM_IDS 7720087411
SUM_NAME_LEN 1615367
```

## ЧТО и ПОЧЕМУ (правило честности)

- VALIDATE (12.2×): the Datara validator is byte-per-byte over a
  `List<Int>` (one `.get()` C-call per byte via the JIT), while the C
  parser indexes a `const char*` directly. The 12× is the per-call JIT
  boundary cost, not algorithmic.
- EXTRACT (4.7×): per record the Datara side allocates 4 substring
  copies (scratch ring) and re-scans for the pattern; C extracts with
  pointer ranges and zero allocations. The gap narrowed from >3000× to
  4.7× **because of a real runtime bug this bench caught and fixed**
  (below).

## Runtime bug caught by this bench (fixed 2026-11-03)

`datara_rt_str_substring` began with `strlen(s)` for bounds clamping —
every interior substring of a large document was O(n). The first bench
run took **73.5 s** in the extract phase; after replacing the strlen
guard with an O(len) `memchr` check (`src/runtime/datara_fs.c`) the same
phase runs in **111 ms** — a 663× fix found by benchmarking honestly.
Edge cases re-verified (interior / clamped / past-end all correct) and
the full `cargo test` suite stays green.

## Known Datara-side limitations recorded on the way

Each was hit while building this bench and recorded as a repro in
PLAN_V152 N2 (none blocks the artifact):

1. `str_byte_at` re-runs `strlen` per call — O(n²) for byte loops over
   large strings; the reader uses `str_bytes()` once instead.
2. Module-level `const` inside a use'd module lowers to 0 at run time.
3. Module-level `mut` state inside a use'd module does not persist
   across function calls (per-function isolation).
4. Module-level `mut` Str globals lose their value (empty-literal init
   infers Int; value lost across returns).
5. `Outcome.ok/err` construction from a use'd module's module-level
   functions yields a mangled Outcome (is_success=false for ok(),
   error_msg = raw pointer).
6. **Behavior-method calls inside a loop that reads a List<Int>
   segfault on both tiers** (T4/T9b repro); the identical body as a
   plain function runs clean and bit-matches C. The bench therefore
   calls plain extractor functions — semantically identical work.

## Reproduce

```bash
python -I bench_json/gen_json.py bench_json/data_10mb.json 10
gcc -O2 -o bench_json/json_c.exe bench_json/json_c.c
./bench_json/json_c.exe bench_json/data_10mb.json
./target/release/forgen.exe run bench_json/json_bench.dtr
```

`data_10mb.json` is not committed (generated deterministically by the
script; `bench_json/.gitignore` keeps it out of the tree).
