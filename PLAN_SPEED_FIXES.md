## P1 — Строки O(n²) в конкатенации (критический, самый большой выигрыш)

**Симптом:** `s = s + "x"` в цикле 200k раз → 6.8 сек (C: 3ms). Каждый `+` копирует строку заново. CPython спасается in-place append при refcount==1 — Datara пока нет.

**Где (точные координаты):** `src/runtime/datara_runtime.c:324` → `datara_rt_str_concat`; scratch-ring: `datara_str_scratch_alloc` (:286), `DATARA_SCRATCH_RING_SIZE` = 1MB (:137); SSO: `DATARA_SSO_MAX_LEN` = 22 (:253). **Важный нюанс:** scratch-ring по дизайну никогда не освобождается («leaks scratch strings by design», :295-302) — каждая конкатенация выделяет новый блок, отсюда O(n²) копирования + рост памяти. Пул компилятора: `src/codegen/cranelift/backend/inst_call.rs:620-781` (drop-вставка для результата concat), `declare_module.rs:342-345` (string_return_funcs). Имплементация уже есть в обоих бэкендах — менять только рантайм, сигнатуры не трогать.

**План фикса (по возрастанию сложности):**
1. **Fast-path в concat**: если LHS — уникальная (refcount==1) мутируемая строка и есть capacity → амортизированный realloc + memcpy хвоста вместо полного копирования. Ожидаемый эффект: strings-ворклоад падает с 6.8s до ~5-15ms (паритет с C).
2. **`StrBuf` в stdlib** (`stdlib/text/`): `push_str`, `push_char`, `build()` — явный мутирующий билдер для пользовательского кода, документировать в доке вместо «наивного +».
3. **Escape/ownership-анализ**: доказать в компиляторе, что LHS не алиасится (усиление существующего ownership-гварда), чтобы fast-path включался автоматически для `mut`-переменных.
4. Опционально: rope/отложенная конкатенация для очень длинных цепочек (после замеров — не раньше).

**Бонус-факт:** оптимизатор уже умеет фьюзить цепочки concat — `src/optimizer/pipeline_fusion.rs:199-249` сворачивает `concat(a, concat(b, c))` в `concat_3/4/5`. Но это не спасает цикл `s = s + "x"`: каждая итерация — отдельный вызов concat с новым scratch-блоком. Поэтому фикс именно в рантайме. При разбивке (P4) вырезать строковый блок в `datara_string.c` вместе с этим фиксом.

**Критерий готовности:** `bench_honest/run_matrix.py --langs datara,c,rust,python,node` → strings: Datara ≤ 2x от C; юнит-тест на refcount-семантику (алиасинг LHS не ломает fast-path); дифференциальный тест вывода строк.

## P2 — Честность бенчмарков: убрать констант-фолдинг из замеров

**Симптом:** Datara-компилятор развернул рекурсивный `fib(35)` в итеративный цикл с константой 35 (видно в `objdump -d`: цикл из 17 итераций, `cmp $0x23`). `sum_loop` свёрнут в немедленное значение `0x11c3793adb7080` (=5000000050000000). Результат «fib 3ms vs C 11ms» — это не скорость рекурсии, а победа оптимизатора. C/Rust тоже умеют fold, но их ворклоады написаны честно.

**План:**
1. Переписать fib/sum-ворклоады в `bench_honest/workloads/` так, чтобы n приходило извне (argv или чтение из stdin). Проблема: пробник `str_to_int("100000000") or 0` упал с `E0944 cannot resolve receiver '.is_success'` — **перед этим починить postfix-`?`/`or` на Outcome от str_to_int или найти работающий способ парсинга argv** (проверить поддержку argv в CLI-рантайме; в `src/` есть только dpm-args, пользовательского argv для программ не обнаружено — возможно, придётся добавить).
2. Если argv нет — ввести `fn args() -> List<Str>` в stdlib (это в любом случае дыра языка для CLI-программ).
3. Перепрогнать матрицу; зафиксировать в README/docs, что fib-числа из замороженной матрицы `docs/data/` (4.77x vs C) — это эффект фолдинга, не рекурсии. Добавить в таблицу колонку «fold: yes/no».
4. Опционально: флаг компилятора `--no-const-fold` для бенчей (но честнее — runtime-input).

**Критерий готовности:** fib(35) через runtime-аргумент; разница Datara vs C на рекурсии показана честно (ожидание: паритет или до 1.5x отставания — рекурсия у C тоже не векторизуется).

## P3 — matmul: векторизация и bounds-check (реальное отставание 2x)

**Симптом:** 11.78ms vs 5.88ms (C -O2). Внутренний цикл `acc += a[i*n+k] * b[k*n+j]` не векторизуется; bounds-check'и на каждый доступ не вынесены.

**План:**
1. LLVM-бэкенд: включить/починить pipeline pass'ы `loop-vectorize` + `slp-vectorizer` для скалярных циклов над flat-массивами. Проверить, что fixed-size массивы `[f64; N]` в LLVM-IR представлены как указатели на линейную память (не как агрегаты), иначе векторизация невозможна.
2. **Hoisting bounds-check**: для циклов вида `while k < n { a[i*n+k] ... }` доказать в компиляторе, что `i*n+k < len` инвариантно/гарантировано диапазоном k, и поднять проверку из тела цикла (или убрать при provable refinement). Это также ускорит sum/dot-циклы.
3. Дифференциальный тест: Cranelift vs LLVM результат matmul побитово совпадает (учесть порядок float-суммирования при векторизации — допуск или детерминированное дерево сложения).
4. Замерить до/после на `bench_honest` + обновить строки в `docs/data/`.

**Критерий готовности:** matmul Datara ≤ 1.3x от C -O2; новые e2e-тесты не пропускаются молча (см. P7, LLVM-гейт).
